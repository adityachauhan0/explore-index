# Cycles 006-007 — the read-size fix, and the regression reverses

## Cycle 005 finding, acted on
H1 (attachment storage, held-out, no index row) had regressed to **+4.3%**.
Root cause from trace-diffing: the treatment agent opened a **68,957-byte**
module in full, then four more reads totalling 55KB. The skill bounded broad
*searches* but said nothing about read *size*.

Fix added to SKILL.md — "Read narrow, not whole":
> `grep`/`glob` first, then `read` with `offset`/`limit`. To confirm a file
> exists, read the top ~60 lines. Only widen if the narrow read actually failed.

## Result: the regression reverses
| task | baseline (n=3) | treatment (n=3) | delta |
|---|---|---|---|
| H1 | 300468 | 212495 | **-29.3%** (was +4.3%) |

H1 treatment trace after the fix: 155,425 tokens, 9 turns. The 68KB read is
gone. What remains is three saturated greps — the next obvious target.

## Baseline trace confirms the mechanism from the other side
The H1 baseline rep3 did a repo-wide `attachment` grep: **637 hits across 77
files**, then read `filesystem-storage.ts` in two chunks (53KB + 560 lines).
Its own closing note:
> "Start at `apps/api/src/modules/data-operations/` instead of repo-wide
> `attachment`, since it matched 637 hits across 77 files (closings, WhatsApp,
> CRM offline IndexedDB) that had nothing to do with disk storage."

The narrow-read rule teaches exactly the lesson the baseline had to learn the
expensive way.
